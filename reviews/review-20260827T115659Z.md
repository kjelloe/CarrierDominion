# Repository review

## Summary

The engine core is in good shape: the reducer is pure, the command vocabulary is validated before it touches state, authority is checked on the untrusted path, the fog filter is shape-checked in both directions, and the pinned fixture now carries both a trajectory and a behaviour hash. The most important thing to fix is that several unit orders mutate state *before* they reject (a parked Manta takes off on a refused order), closely followed by `set_route` accepting legs beyond the map edge that every sibling command refuses. The LAN server also has two operational gaps worth closing before a playtest weekend: a resumed war can never reopen its war room, and any engine assertion inside the tick pump takes the whole server down.

## Findings

### R-001 — Rejected unit orders still lift a parked Manta off the runway

- **Severity:** major
- **Area:** game code
- **Location:** `engine/reducer.js:485-486`, `engine/reducer.js:504-505`, `engine/reducer.js:373-374`
- **Problem:** `applyUnitMove`, `applyUnitAttack` and `applyUnitEscort` call `liftOff(unit)` and only *then* run the check that can reject the command (the off-map bounds test at line 486, the `designated()` lookup at line 505, the lighter test at line 374). `liftOff` sets `state = UNIT_ACTIVE`, clears `landedIsland` and sets throttle to 100. A rejected command therefore leaves the unit airborne with whatever `order` it had before, and the client receives `EVT_COMMAND_REJECTED` for a command that visibly did something.
- **Impact:** A player who clicks Attack on a contact that has just vanished, or clicks the sea past the chart margin, watches their landed Manta take off and fly its previous order while the UI says the order was refused. It also breaks the contract in docs/01 ("malformed commands are dropped") that a rejection is a no-op.
- **Fix:** Move `liftOff(unit)` after the last rejecting check in each function. In `applyUnitMove` put the `sizeUnits` test before `liftOff`; in `applyUnitAttack` resolve `designated()` first; in `applyUnitEscort` test `unit.kind === KIND_LIGHTER` first.
- **Verify:** New test in `test/engine_runway.test.js`: land a Manta on a friendly runway, issue `order_unit_attack` at a `targetId` that does not exist, assert `unit.state === UNIT_LANDED` and that the only event is code 1.

### R-002 — `set_route` accepts legs beyond the map edge; every sibling command refuses them

- **Severity:** major
- **Area:** game code
- **Location:** `engine/commands.js:259-262`, `engine/reducer.js:443-447`, `engine/route.js:26`
- **Problem:** `validateCommand` for `set_route` only checks each coordinate `>= 0`; `setRoute` in `route.js` has no upper bound check (no reference to `sizeUnits` anywhere in that file); `applyRoute` copies the first leg straight into `courseX/courseY` or `targetX/targetY`. By contrast `applyCourse` (`reducer.js:165`) and `applyUnitMove` (`reducer.js:486`) both reject `x > sizeUnits || y > sizeUnits`. docs/05 §"What the watchdog trips on" states "legs are validated on the way in, and this is the tripwire for one that arrived another way" — the tripwire (`server/watch.js:140-154`) is currently the *only* validation.
- **Impact:** Any client (including a modified one on the LAN) can steer a hull or aircraft at a point outside the world; the watchdog reports it as a finding on every tick rather than the command being refused.
- **Fix:** In `applyRoute`, before `setRoute(...)`, loop over `points` and `reject(next)` if any `x` or `y` exceeds `next.params.sizeUnits` (the validator cannot do it — it has no state). Do it for both the unit and the carrier branch.
- **Verify:** Test in `test/engine_route.test.js`: `set_route` with `points: [sizeUnits + 1, 0]` on a carrier yields event code 1 and leaves `carrier.route.length === 0`.

### R-003 — Enemy aircraft on a runway, on the ramp or on final approach are invisible to everyone, referee included

- **Severity:** major
- **Area:** game code
- **Location:** `shared/view.js:407`, `shared/view.js:587`
- **Problem:** Both `buildView` and `refereeView` only emit an enemy unit when `unit.state === 1 || unit.state === 2` (ACTIVE / RETURNING). `engine/units.js:21-27` also defines `UNIT_LANDED = 4`, `UNIT_ON_DECK = 5`, `UNIT_LAUNCHING = 6`, `UNIT_DOCKING = 7`. A Manta parked on a captured island runway, a fuelled Manta sitting on the enemy's deck, and an aircraft flying its recovery envelope are all physically on the map and inside radar reach, yet never reach the contact list. docs/03 says enemy hulls appear "inside your own detection range" with no state exception, and docs/03 says the referee sees "every hull".
- **Impact:** A Manta becomes untargetable the moment it enters the docking envelope, and an island runway can hold a whole enemy air group in plain sight of a fleet that cannot see it. The referee view — which exists precisely so an observer sees *everything* — has the same hole.
- **Fix:** Replace the state test with "anything not stowed and not lost": `unit.state !== UNIT_STOWED && unit.state !== UNIT_LOST` (import the constants rather than repeating literals). If ON_DECK/LAUNCHING are meant to be hidden inside the ship's hull, say so in a comment and in docs/03; LANDED and DOCKING should certainly be visible.
- **Verify:** Add to `test/shared_view.test.js`: force an enemy Manta to `UNIT_DOCKING` / `UNIT_LANDED` inside the observer's radar and assert it appears as a contact; assert the referee view lists it.

### R-004 — A resumed war can never return to the war room

- **Severity:** major
- **Area:** game code
- **Location:** `server/app.js:103-110`, `server/app.js:475-477`, `server/index.js:29-31`
- **Problem:** `app.lobby` is created only when `resumedGame === -1`. After a successful resume, `app.lobby === 0`, so `reopenRoom` returns `'there is no war room'`. docs/03 promises "the SAME join code holds — one code hands friends a whole evening", and `index.js` documents `RESUME=auto` as "the service setting" — meaning the deployed server is *always* in this state after any restart.
- **Impact:** On the hosted box, any process restart mid-evening leaves the table with a war they can finish but no room to start the next one; they have to restart the server by hand.
- **Fix:** Create the lobby whenever `options.lobby === true`, seeding it with the saved options and `status: 'running'` when a resume succeeded:
  ```js
  lobby: options.lobby === true
    ? createLobby(bootId, resumedGame === -1 ? defaults : { ...defaults, ...options.resume.options })
    : 0,
  ...
  if (resumedGame !== -1 && app.lobby !== 0) app.lobby.status = 'running';
  ```
  Then `reopenRoom` works after the resumed war ends, and `startWar` produces a fresh war under the same code.
- **Verify:** Test in `test/server_save.test.js`: create an app with `lobby: true, resume: saved`, assert `app.lobby !== 0`, `app.lobby.status === 'running'`, `app.health().joinCode !== ''`.

### R-005 — An engine assertion inside the clock pump crashes the LAN server and loses up to 30 s of war

- **Severity:** major
- **Area:** game code
- **Location:** `server/app.js:569-577`, `server/clock.js:48-51`, `shared/fixed.js:52-57`
- **Problem:** `shared/fixed.js` throws `RangeError` from `assertExact`, `isqrt`, `divFixed` and `mulDiv` on purpose, and `shared/statehash.js` throws on a dirty state. The clock callback calls `stepGame` with no `try/catch`, inside a `setInterval`, and `index.js` installs no `uncaughtException` handler. Any such throw is an unhandled exception that terminates the process; the shutdown handlers on SIGINT/SIGTERM do not run for an uncaught exception, so the final `saveNow()` never happens and the last `AUTOSAVE_MS` (30 s) of the command log is gone.
- **Impact:** A single arithmetic edge on the 64-island map (the class of bug the watchdog exists to find) ends the evening for every seat and loses the tail of the log.
- **Fix:** Wrap the body of the clock callback: on throw, log the error with the tick, `stopClock(app.clock)`, call `app.saveNow()` (the state before the failed tick is still intact because `apply` copies before mutating), and set a `app.halted` reason that `/healthz` reports. Do not attempt to keep ticking.
- **Verify:** Test in `test/server_clock.test.js` or `server_ws.test.js`: create an app whose `game.state` is doctored so the next tick throws (e.g. set `carriers[0].x = 2**40`), pump the clock once, assert the process is still alive, `app.clock.running === false`, and the save file exists with the pre-failure tick.

### R-006 — A player back after the grace window never gets *their* seat, and `reclaim`'s late-return branch is dead

- **Severity:** minor
- **Area:** game code
- **Location:** `server/app.js:187-195`, `server/app.js:280-284`, `server/reconnect.js:57-60`
- **Problem:** `sweepHeldSeats` runs at the top of every connection and calls `release(app.holder, record.team)`, which deletes the record from `holder.held`. `reclaim` then searches `holder.held` and cannot find the token, so its "expired but not taken" branch at `reconnect.js:57-60` can never execute — the record is already gone. The player falls through to `claimTeam()`, which hands out the *lowest* free team, discards their name, and answers `resumed: 0`. docs/03 says "A player who was late back is still let in if the seat has not been claimed by anyone else", which happens only by coincidence when their team is also the lowest free one.
- **Impact:** In a 3+ seat war a commander who was late back can find themselves at a different carrier than the one they were flying, with the AI still flying theirs.
- **Fix:** In `sweepHeldSeats`, mark `record.aiTaken = 1` and enqueue `set_ai` but do **not** `release`; let `reclaim` honour the token (its existing branch does the right thing) and have `claimTeam` treat `aiTaken === 1` holds as free for newcomers. Remove the record on successful reclaim or when a newcomer takes the team.
- **Verify:** Extend `test/server_reconnect.test.js`: hold team 1, advance `nowFn` past `GRACE_MS`, run the sweep, then `reclaim` with the token and assert it returns the record for team 1.

### R-007 — The autosave test depends on wall-clock timing

- **Severity:** minor
- **Area:** tests
- **Location:** `test/server_save.test.js:92-98`
- **Problem:** The test listens on a real port, sleeps 200 ms, and asserts `saved.tick > 0`. With `msPerTick` around 50 ms that is roughly four ticks of headroom on an idle machine and zero on a loaded CI runner (the same class of flake docs/05 describes for the probe sweep).
- **Impact:** Intermittent red gate in CI with nothing wrong.
- **Fix:** Drive the clock directly: call `pump(app.clock, app.clock.originMs + rules.rules.msPerTick * 3)` instead of sleeping, or `stepGame(app.game)` once before `saveNow()` and assert on that tick.
- **Verify:** Run the file under `taskset -c 0 stress-ng`-style load or simply remove the sleep and confirm it still passes deterministically.

### R-008 — The new weather probe reads the scope by hard-coded pixel geometry

- **Severity:** minor
- **Area:** tests
- **Location:** `debugging/probes/weather.mjs` (uncommitted diff, `SCOPE_READER`, lines 663-676 of the diff)
- **Problem:** `SCOPE_READER` bakes in "pad 10, helm width 250" from `client/render/instruments.js`. The engine-review skill's own failure class "A probe that selects the UI by position" (`.claude/skills/engine-review/SKILL.md:155-161`) describes exactly this: the next panel re-layout silently moves the sample window onto a different instrument and the lightning check passes or fails on the wrong pixels.
- **Impact:** The `lit > dark + 3` assertion can go green while measuring the helm gauge.
- **Fix:** Export the scope rectangle from `instruments.js` (e.g. `window.__scopeRect` alongside `__debugView`) and read it in the probe, or have `instruments.js` draw the scope onto its own named canvas.
- **Verify:** Change `pad` in `instruments.js` and confirm the probe still reads the scope box.

### R-009 — Personal permission allow-list is broad enough to bypass the slice skill's branch rules

- **Severity:** minor
- **Area:** claude-config
- **Location:** `.claude/settings.local.json:14,17,20,22,25,32`
- **Problem:** The allow list grants `Bash(node *)`, `Bash(node -e ' *)`, `Bash(python3 *)`, `Bash(python3 -)`, `Bash(sed *)`, and `Bash(git push *)`. The first five are arbitrary code execution (including `sed -i` over any file in the three working directories), and `git push *` permits pushing to `main`/`dev`, which `.claude/skills/slice/SKILL.md:126-128` forbids. The file is gitignored, but it is what governs every session in this checkout.
- **Impact:** No prompt stands between an agent and `git push origin dev_night:main` or a stray `sed -i` across `game-ops/`.
- **Fix:** Narrow to the actual invocations: `Bash(git push origin dev_night)`, `Bash(node test/*)`, `Bash(node tools/*)`, `Bash(node debugging/probes/*)`, and drop the wildcard `node *`, `python3 *`, `sed *` entries.
- **Verify:** Attempt `git push origin dev_night:main` in a session and confirm it prompts.

### R-011 — `set_route` is the only order that refuses a landed Manta

- **Severity:** nit
- **Area:** game code
- **Location:** `engine/reducer.js:418`
- **Problem:** `applyRoute` rejects unless `state` is ACTIVE or RETURNING, while move/attack/escort/land/recall all accept `UNIT_LANDED` and `liftOff` first. A player with a Manta on an island runway can click a single waypoint but not lay a PROG course.
- **Impact:** Inconsistent affordance; the client's route tool fails silently on a parked aircraft.
- **Fix:** Accept `UNIT_LANDED` and call `liftOff(unit)` after `points` is validated (see R-001 for ordering).
- **Verify:** Test: landed Manta + `set_route` with two legs → `state === UNIT_ACTIVE`, `route.length === 2`.

### R-012 — Session tokens are `Math.random` and the URL parser matches any `token=` substring

- **Severity:** nit
- **Area:** game code
- **Location:** `server/app.js:101`, `server/app.js:178-183`
- **Problem:** The seat token is `Math.random().toString(36).slice(2, 12)`; `tokenFrom` uses `indexOf('token=')`, which also matches `?xtoken=`. On a LAN behind a join code the exposure is small, but the token is what lets someone take over a held carrier.
- **Impact:** A guessable token allows seat hijack during the grace window.
- **Fix:** `crypto.randomBytes(12).toString('base64url')` for the default `tokenFn`; parse with `new URL(req.url, 'http://x').searchParams.get('token')`.
- **Verify:** `test/server_reconnect.test.js` asserts token length ≥ 16 and that `?xtoken=abc` does not reclaim.

## Test coverage gaps

- No test asserts that a *rejected* unit order leaves the unit's `state`, `order` and `landedIsland` untouched (R-001).
- No test sends a `set_route` leg beyond `sizeUnits` and expects rejection (R-002).
- `shared_view.test.js` brands enemy fields but never places an enemy unit in states 4–7 inside radar reach (R-003).
- No test creates an app with `lobby: true` and a resume save and checks the room exists (R-004).
- No test makes the clock callback throw and checks the server's behaviour (R-005).
- No test exercises "hold → grace expires → sweep → reclaim with the original token" end to end (R-006).
- `reopenRoom` + `startWar` with a *smaller* `teams` option than the number of seated players (a seat whose `team >= teams.length` would receive `snapshot.views[team] === undefined`) is unexercised; `lobby.js` was not read deeply enough to confirm a guard exists — worth a test either way.
- The `weather` probe's lightning-on-scope check has no unit-level counterpart; `drawStormClutter` in `client/render/radar.js` could be tested in `client_pure.test.js` with a stub 2D context.
